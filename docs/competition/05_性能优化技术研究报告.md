# Rust 与 C 版 EXT4 性能优化技术研究报告

**文档性质**：学术型研究报告，包含量化测试数据、归因分析、优化技术、理论上限推导与明确的研究结论。
**研究对象**：运行于 Asterinas（Rust framekernel，OSTD 非特权运行环境，兼容 Linux ABI）之上的 Rust EXT4 实现，与 Linux 发行版的 C 版 EXT4 在同口径下对照。
**口径声明**：本报告所有性能数字均为诚实口径——关闭自研投机数据读缓存（`ext4fs.direct_read_cache`）、drop-caches 公平基线、fio 取 `direct=1 numjobs=1` 的中位数。历史上投机缓存开启时得到的 read 127% / write 39% 已被废弃，不用于本报告任何结论。

---

## 摘要

本研究在 Rust framekernel 操作系统 Asterinas 上实现并优化了支持 Extent 与 JBD2 完整日志的 EXT4 文件系统，系统性地探索了面向 RustOS 架构、且在保持崩溃一致性语义前提下的性能优化技术。研究方法以延迟归因为驱动：在文件系统、virtio、锁与 JBD2 四层进行纳秒级埋点，并辅以 ext4／ext2／ramfs 三文件系统的对照实验，将性能差距分解为可独立攻击的成分，再据此设计优化。归因将瓶颈定位为三类——大块单流受限于平台 virtio 往返、小块受限于每操作固定开销、真实应用写路径受限于"每次提交把文件缓存清零、逐 4 KiB 同步回填、逐页日志 handle"三者的乘积。在不触碰 fsync 持久化安全点、不放松 JBD2 语义的前提下，本研究落地了十二项优化技术。

量化结果如下。fio O_DIRECT 顺序读写从优化前小块 16–24% / 写 4K 约 20% 提升至读 86–123% / 写 76–121%，其中大块（256K、1M）已追平乃至反超 Linux。真实应用 SQLite speedtest1 相对 Linux 的占比从 2.97% 提升至 21.92%，对应 7.4 倍的相对提升（墙钟耗时由 2022s 降至 234.9s），全程数据完整性校验通过。并发同文件写经共享锁直接 I/O 改造后达到 Linux 的 165%–187%。这一优化幅度数量级地超过赛题"≥5%"的要求。研究进一步通过三文件系统对照（ext2 94.91% / ramfs 95.87%）与一项类别内数学下限推导，诚实地界定了剩余差距的结构性归因与现实可达上限，并提炼出可迁移于 RustOS 存储层的优化方法论。

## 1. 研究背景与问题陈述

### 1.1 一致性与性能的结构性张力

文件系统以 JBD2 日志保障崩溃一致性：元数据在落到 home 位置之前先以事务形式顺序写入日志区，提交记录安全落盘后方可回写 home。这一"先日志、后数据"的次序约束是崩溃可恢复的根据，却也直接与吞吐和延迟为敌——它放大了元数据 I/O，并把本可并行或乱序的写入强制串行化。如何在保持一致性语义的同时把性能逼近无日志基线，是文件系统领域的经典难题。

### 1.2 RustOS / framekernel 的机会与约束

Asterinas 的 OSTD 非特权运行环境与 Rust 所有权语义，一方面以编译期保证消除了大量内存安全风险，另一方面也以清晰的所有权边界为"以缓存和批量化摊薄每操作开销"提供了可推理的结构。但该平台也带来约束：块设备经 virtio-blk 访问，设备往返延迟由平台决定，文件系统层无法绕过；且某些传统内核的优化手段（如复杂的后台回写线程）在非特权环境中实现代价高昂。本研究的问题正是在这一机会与约束的交汇处展开。

### 1.3 研究问题

本研究试图回答三个递进的问题：(Q1) 在 framekernel 架构下，Rust EXT4 相对 C 版 EXT4 的性能差距，其成分如何被定量分解、各成分的归属为何；(Q2) 在不破坏一致性与持久化语义的前提下，哪些优化技术能够有效地消除这些成分，其收益如何被量化与验证；(Q3) 剩余差距的结构性根源是什么，其现实可达的上限在哪里，是平台地板还是文件系统的实现选择。

## 2. 实验方法与口径

### 2.1 公平对照原则

所有对照实验在同一容器、同一 QEMU/KVM、同一 virtio 块设备、同一轮次中交替运行 Asterinas 与 Linux EXT4，并在每个测试项执行前清空宿主页缓存，使两侧面对相同的冷缓存初始条件。虚拟机配置为 8 GiB 内存、单处理器、KVM 加速。单处理器的选择有意把并发实验的扩展性归因从硬件并行中剥离，使观察到的吞吐变化能够归因到锁结构而非核数。比值定义为：fio 比值等于 Asterinas 带宽除以 Linux 带宽，SQLite 比值等于 Linux 耗时除以 Asterinas 耗时。

### 2.2 诚实口径与其必要性

性能数据一律在关闭自研投机数据读缓存的条件下采集。这一纪律并非保守，而是必要：投机缓存以牺牲某些一致性边界为代价放大读数，将其计入成绩会系统性地高估真实能力，并使优化前后的对比失去意义。本报告因此显式废弃投机缓存开启时的历史数字，并在每一处数据旁标注口径。

### 2.3 延迟归因驱动的方法学

本研究方法学的核心，是把"凭直觉优化"替换为"先归因、再优化、并验证归因确被缩小"的闭环，它由三个互补的工具组成。

**四层纳秒级 profiling**。在文件系统、virtio、锁与 JBD2 四个层次埋设纳秒级计时（由启动参数 `ext4fs.phase2_profile=1` 门控），对每一类操作产出各路径的耗时占比表。这使"瓶颈在哪一层"成为可测量的事实而非猜测。

**三文件系统三角对照**。在同平台、同负载下对照三种文件系统——带日志的本 ext4、无日志的 Asterinas 原生 ext2、内存盘 ramfs。其逻辑是：ramfs 几乎不含设备 I/O，ext2 含设备 I/O 但不含日志，本 ext4 二者皆含；三者的差值因此可以把"平台 I/O 地板"与"日志写路径成本"清晰地分离开。

**守底门控的制度化**。每一步优化之后重跑崩溃、并发、fsync 与 SQLite 完整性守底，并重跑 profiling 确认本步攻击的成分确已缩小。这把"优化不得引入回归、且必须确有收益"变成强制流程，是对此前"未 profile 先动手而被回退"教训的制度化回应。

## 3. 基线性能与瓶颈归因

### 3.1 fio O_DIRECT：三类瓶颈的分离

以裸盘（`/dev/vda`）读写为参照，对 ext4 的 O_DIRECT 路径做归因，得到三类性质不同的瓶颈。其一，大块单流时 ext4 的带宽逼近裸盘，说明此时瓶颈在 block 与 virtio 层，属平台层、跨文件系统通用，非 ext4 域内可解。其二，小块时每请求的固定开销（映射查询、元数据读、handle 建立）占比上升，这部分落在 ext4 域内，是最具优化空间的成分。其三，多线程同文件读写时吞吐被锁封顶，瓶颈在并发控制——per-inode 互斥锁横跨设备等待，把本可并行的请求串行化。三类瓶颈的攻击手段截然不同，分别对应缓存、批量化与锁改造，因此必须先分离再优化。

### 3.2 SQLite 真实应用：2.97% 的结构性解释

诊断时点，SQLite speedtest1 仅达 Linux 的 2.97%（2022s 对约 60s）。三文件系统三角对照立即锁定了差距的归属：

| 文件系统 | 相对 Linux | 含义 |
|---|---:|---|
| ext4（带日志，本实现） | 2.97%（起点） | 损失几乎全部集中于带日志的写路径 |
| ext2（无日志，Asterinas 原生） | 94.91% | 平台 I/O 地板很薄，不是瓶颈 |
| ramfs（内存盘） | 95.87% | 同上 |

ext2 与 ramfs 同在约 95%，证明 Asterinas 的平台 I/O 并不构成主要损失；而本 ext4 独低至 3%，说明差距几乎全部来自二者之间的唯一区别——日志写路径。进一步看 speedtest1 各子测试的读写分野（page_cache=1，已完成的 11 项）：

| 类型 | 代表子测试 | 相对 Linux 的慢倍数 |
|---|---|---|
| 读（无索引 SELECT） | 140 / 142 / 145 | 约 1.0 倍（持平 Linux） |
| 读（有索引 SELECT） | 160 / 161 / 170 | 约 1.8 倍 |
| 写（无索引 INSERT） | 100 | 27.9 倍 |
| 写（有主键乱序 INSERT） | 120 | 243.8 倍 |
| 写（CREATE INDEX） | 150 | 126.7 倍 |

读路径已具竞争力，约三十倍的总差距集中在写路径。把一次 SQLite 写事务展开，其代价由三个实现选择相乘而成：

```
每写映射检查 ≈41%：每次写都从 virtio 重读 extent 树块——上一轮 fsync 已把缓存清零
慢路径逐页 journaled 分配 ≈32%：全局锁 + handle + 逐块树下沉 + 位图
每次 COMMIT 的 fsync + 逐 4 KiB bio ≈24%：且 evict_all 把整文件缓存丢光，回到第一项的恶性循环
```

这一展开给出了关键判断：约三十倍的差距并非"日志的必然代价"，而是"每次提交清零缓存、逐 4 KiB 同步 I/O、逐页日志 handle"三个**可消除的实现选择**的乘积，且三者的修复点都落在 fsync 安全点上，不触碰持久化语义。这一判断把后续优化从"是否要放弃日志"的死胡同里解放出来。

## 4. 优化技术

本节按攻击的瓶颈成分组织，逐项给出动机、设计与量化收益。所有技术均在保持 JBD2 完整语义、不触碰 fsync 持久化安全点的前提下落地。

### 4.1 读路径与每操作固定开销

针对 §3.1 的第二类瓶颈（小块每请求固定开销）与读路径，落地五项技术。

**T1 Extent 映射计划缓存**。把逻辑到物理的映射结果缓存，避免每次读写都重复下沉 Extent 树，直接削减小块路径的固定开销。

**T2 inode 元数据缓存与生成数失效协议**。缓存 stat 元数据以免重复读 inode 块；失效统一锚定于变更收敛点，并以生成数防止读出后被并发改写的 TOCTOU。该协议是后续多套缓存共享的失效基座。

**T3 relatime 节流**。把访问时间的更新节流为每秒至多一次日志，消除读操作引发的高频元数据日志。

**T4 覆盖写快路径**。当写区间不越过文件尾且已全部映射时，判定为纯覆盖，绕过 JBD2 handle，仅置脏页并延迟到 fsync。这是写路径免税的关键——它使绝大多数 in-place 更新不再为日志付费，是 fio 写 4K 从约 20% 升至 76% 的主因之一。

**T5 大块连续映射合并与投机预读**。把连续映射合成大 bio 一次提交，并对顺序 O_DIRECT 读做投机预读，使大块带宽逼近设备上限。

读侧的总体效果是：小块读从优化前的 16–24% 提升至 84–87%（约 2.6 至 5.2 倍），大块读追平乃至反超 Linux。

### 4.2 真实应用写路径：归因驱动的递进优化

针对 §3.2 展开的三项乘积成分，按 profiling 指示的顺序递进优化，每一步的 SQLite 总耗时变化均经实测确认。

**T9 fsync 保留 clean 页**。早期实现在写回后把整个文件的页（含未脏的 clean 页）一并丢弃，使每次提交后缓存归零、后续读与部分页写的回填退化为对设备的逐 4 KiB 同步读，构成恶性循环。修复是写回后只标记 clean 而不丢弃，把内存上界回落到工作集规模，与无日志文件系统同构。实测使总耗时从 2010.7s 降至 1868.2s。

**T10 fsync 安全点批量写回**。把逐脏页一个 handle、一个 4 KiB bio 的写回，改为按连续脏页区间合并 handle 与 bio。对已分配块的纯数据写回在 ordered 模式下本不需要 JBD2 handle（数据非元数据），合并后显著降低 per-page 开销。实测降至 1772.4s。

**T8 unwritten extent 与写时预分配**。引入 unwritten 语义并把每次小写的预分配块数从 1 提高（实现中为 32），使追加场景以批量分配替代逐块树下沉，崩溃后多出的尾部块至多构成空间泄漏而不暴露脏数据。实测降至 1332.2s（3.86%）。

**T6 设备块缓存（DeviceBlockCache）**。这是攻击 §3.2 中占比最大的第一项成分（每写从 virtio 重读 extent 树块，约 41%）的核心技术。在 adapter 层引入设备 home 块内容的 write-through 镜像（约 32 MiB、LRU），使元数据块读命中内存。其放置位置经过专门设计：镜像位于 JBD2 overlay 之下，于是检查点与恢复对 home 的写天然穿透该镜像、无需特殊处理，唯一需要显式失效的是绕过它的 O_DIRECT 数据 bio。实测命中率约 98.5%，总耗时由 1332.2s 骤降至 454.3s（11.26%），是单项收益最大的技术。

**T7 写快路径的"ext2 化"**。以 per-inode 的写覆盖区间集（WrittenCoverage）把覆盖写判定退化为一次前驱查询，配合直接经 VmReader 写入与 per-inode 粒度的元数据缓存失效，使覆盖写路径接近无日志文件系统的纯内存命中。该结构维持 `coverage ⊆ truth` 不变量——以"miss 时走权威的树查询填充、prepare 后补全有界尾段、truncate/unlink/rename 时失效"保证区间集只会少报不会多报，从而判定安全。实测降至 243.9s（20.88%）。

**T11 精简准备（lean prepare）**。对全部落在已分配区间的写，把准备阶段的三遍树查询合并为单遍探测，削减冗余。实测降至 234.9s（21.92%）。

### 4.3 并发优化

**T12 共享锁直接 I/O**。把 per-inode/per-dir 正确性锁由互斥锁升级为读写锁，使 `page_cache=0` 下经映射验证的纯覆盖 O_DIRECT 写在共享锁内完成判定与提交、O_DIRECT 读同享，而映射变更方持独占锁。其 TOCTOU 安全性由"判定纯覆盖所依据的映射只能被持独占锁者改变、而独占与共享互斥"保证。该技术对应 Linux 共享 `i_rwsem` 的覆盖写语义，拆除了单文件并发被锁封顶的瓶颈。

| 目标 | 线程数 | Asterinas (MB/s) | Linux (MB/s) | 比值 |
|---|:--:|---:|---:|---:|
| ext4 写 | 2 | 6024 | 3641 | 165.5% |

### 5.4 对赛题"≥5% 提升"指标的对照

赛题优秀档要求所探索的优化技术实现不低于 5% 的性能提升。本研究的单项技术即远超该线：设备块缓存一项就把 SQLite 总耗时从 1332.2s 压到 454.3s（降约 66%），写快路径再降约 46%；读侧小块提升 2.6 至 5.2 倍，写 4K 由约 20% 升至 76%。优化幅度在数量级上超过 5% 门槛。

## 6. 剩余差距之一：virtio 平台地板（小块缺口归因）

fio 小块（4K、16K）读约 84–86%、写约 75–76%，距 90% 仍有缺口。本节论证该缺口的归属并非本 ext4 实现，而是平台层。证据链有三环。其一，Asterinas 原生 ext2——一个无日志、实现成熟的文件系统——在同平台、同口径下做相同的小块 fio，同样止步于 82–85%，与本 ext4 的小块上限一致。其二，大块时本 ext4 的带宽逼近裸盘 `/dev/vda`，说明 ext4 域内的每请求固定开销在大块时已被摊薄殆尽。其三，将一、二两点合并即得结论：小块的剩余缺口来自 virtio 设备往返这一每请求固定成本，它是平台层的、跨文件系统通用的，本 ext4 与原生 ext2 共享同一道地板。因此该缺口指向的是一个跨文件系统的平台优化方向，超出本赛题 ext4 的范围。

## 7. 剩余差距之二：SQLite 上限的理论分析

### 7.1 不是根本极限，而是"付税方式"的差异

Linux EXT4 带完整 JBD2 跑完 speedtest1 约需 51 秒。因此昂贵的并非日志本身，而是**为日志付税的方式**。Linux 采用延迟分配（delalloc），把每页的元数据成本摊薄到每个 extent（趋近于零）；本实现采用"写时同步转换"，对每 4 KiB 的新分配写全额支付分配与转换成本。差距的根因是付税方式，而非是否带日志。

### 7.2 类别内的数学下限

可以对"写时同步转换"这一类方法估出一个下限。speedtest1 约产生 549K 次新分配写，每次至少包含零填充（约 30 µs）、handle 与 overlay 维护（约 60–100 µs）、unwritten 转换（约 30–50 µs）。即便理想化到每次 100 µs，仅此一项即约 55 秒——这已逼近"达到 Linux 90%"所对应的约 57 秒总预算。由此可推：在"写时同步转换"类别内，理论最优约 110–120 秒（43–46%，且无已知路径可达），现实可达约 190–210 秒（24–27%）。实测 234.9 秒（21.92%）已接近该现实上限。优化曲线的边际递减也印证了这一点：设备块缓存降 66%、写快路径降 46%、精简准备仅降 4%，收益迅速趋平。

### 7.3 突破到 90% 的唯一通道及其代价

要把 SQLite 从约 25% 推向 90%，唯一通道是引入延迟分配与后台回写，把同步转换成本摊薄。但该通道有严格的前置条件链：必须先钉死"乱序写回损坏"的精确根因（其本质是"inode 大小先于脏页"这一隐式不变量在延迟分配下不再成立），再构建安全的写回驱动（OSTD 级的后台 flusher），方能解开延迟分配本体并为其补全崩溃语义。这条链估计需 2–4 周的工程投入，且其前置正是当前系统已知的脆弱点，因此被列为赛后 hardening 而非本期目标。这一判断本身也是研究结论的一部分：它界定了"在不重写写回驱动的前提下，本类方法的现实天花板"。

## 8. 与 C 版 EXT4 的对比及研究结论

### 8.1 维度对比

| 维度 | Linux C 版 EXT4 | 本 Rust 实现 | 说明 |
|---|---|---|---|
| 顺序读（大块） | 100% | 95–123% | 追平/反超 |
| 顺序写（256K） | 100% | 121% | 反超 |
| 顺序读写（小块） | 100% | 75–87% | 缺口=virtio 平台地板（ext2 同上限） |
| SQLite 真实应用 | 100%（约 51s） | 21.92%（235s） | 付税方式差异（同步转换 vs 延迟分配） |
| 并发同文件写 | 100% | 165–187% | 共享锁直接 I/O 线性扩展 |
| 内存安全 | 手动管理 | Rust 所有权（编译期保证） | 规避缓冲区溢出/悬垂指针 |
| 崩溃恢复 | JBD2 含撤销 | JBD2（撤销待补） | guest-crash 全覆盖 |

### 8.2 研究结论

**结论一：Rust EXT4 在合成负载上可以接近乃至反超 C 版 EXT4。** 大块顺序与并发同文件写已追平或反超 Linux；小块的剩余缺口经三文件系统对照被证明为平台 virtio 地板，与原生 ext2 共享同一上限，并非文件系统实现的短板。

**结论二：强一致性与高性能并非不可兼得。** 在保持 JBD2 完整语义、不触碰 fsync 安全点的前提下，SQLite 写性能取得 7.4 倍的相对提升。这直接反驳了"约三十倍差距是日志的必然代价"的假设——差距实为三个可消除的实现选择的乘积，可被系统性地逐项消去。

**结论三：延迟归因驱动是达成上述结果的关键方法。** 四层纳秒级 profiling、三文件系统三角对照与守底门控的组合，使每一步优化都"先归因、可验证、不回退"。这套方法学本身与具体文件系统弱耦合，可迁移于其他 RustOS 存储层组件。

**结论四：本研究产出了一组可复用的优化技术。** 设备块缓存（位于日志 overlay 之下的设备块 write-through 镜像）、写覆盖区间集（以前驱查询实现的覆盖写快路径）、生成数失效协议、fsync 安全点批量写回、unwritten extent 与物理预分配、共享锁直接 I/O——这些技术面向 RustOS/framekernel 架构、与具体文件系统弱耦合，构成可迁移的优化模式。

## 9. 负结果与方法论教训

负结果对方法论的价值不亚于正结果，本研究据实记录三类。

**其一，延迟分配被"乱序写回损坏"挡住。** 延迟分配的前置是乱序写回的正确性，而这恰是当前系统的已知脆弱点（"大小先于脏页"的隐式不变量在延迟分配下崩溃）。早期的延迟分配实验确实触发了数据损坏，这是把它降级为赛后工程、而非贸然推进的直接依据。教训是：在隐式不变量被断言固定之前，不做依赖其反面的投机优化。

**其二，"仅 size 的追加"实测净负。** 一项推迟 unwritten 转换、只更新文件大小的尝试在三种配置下分别测得 462.9 / 312.8 / 468.0 秒，均劣于其基线，且伴随一个尚未解释的读侧约 30% 回退，故被回退保留为补丁。教训是：批量化或推迟必须由占比表确认其攻击面确被缩小，否则可能净负。

**其三，"先核实、再实现"两度避免了无效投入。** 早期一次批量化只合并了 bio 而未消除逐页 handle，且当时占比最大的成分仍在掩盖收益，结果只得到 3% 的改善；另一次拟做"真 fdatasync"优化，在动手前由计数器证明 fsync 桶实测仅占 28.6 秒（提交实由批量轮转而非 fsync 驱动），从而避免了在错误瓶颈上的投入。教训是：profiling 计数器应先于代码，归因未经确认不动手。

## 10. 结论与展望

本研究在 RustOS（Asterinas framekernel）上实现并优化了带 JBD2 完整日志的 EXT4，以延迟归因驱动的方法学定位瓶颈、落地十二项优化技术，量化取得 fio 读写 76–123%、SQLite 相对提升 7.4 倍（2.97% → 21.92%）、并发 165–187% 的结果，优化幅度数量级超过赛题门槛，并以三文件系统对照与类别内下限推导诚实地界定了剩余差距的结构性归因与现实上限。研究表明：在 framekernel 架构下，强一致与高性能可以在合成负载上兼得，真实应用的差距主要源于付税方式而非日志本身；其唯一的进一步突破通道（延迟分配 + 后台回写）已被清晰地定位，并以其前置不变量的加固为条件。所产出的优化技术与方法学对 RustOS 存储层设计具有可迁移的参考价值。
