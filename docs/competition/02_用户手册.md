# 用户手册：Asterinas EXT4 文件系统

**适用范围**：本手册面向使用者与评测者，说明如何在 Asterinas 上获取、构建、运行本 EXT4 文件系统，如何挂载与配置、如何执行功能与性能测试并复现 benchmark，以及现有功能的边界与常见问题的处置。
**代码基线**：分支 `feature-sqlite-phase-6`。除特别说明外，所有命令在仓库根目录 `asterinas/` 下执行；测试脚本会自行管理 Docker 容器与 QEMU 进程，使用者无需手动准备虚拟机。
**与其他文档的关系**：系统内部结构见《架构设计文档》，测试方法与结果见《测试文档》，性能口径与优化技术见《性能优化技术研究报告》。本手册只关注"如何使用"。

---

## 1. 概述

本系统是运行于 Asterinas framekernel 之上、以 Rust 实现的 EXT4 文件系统。从使用者的角度看，它表现为一个可挂载于 virtio 块设备、对应用透明地提供标准 POSIX 文件语义的内核文件系统，其能力包括：

- POSIX 核心接口：`create`、`open`、`close`、`read`、`write`、`lseek`、`stat`、`truncate` 以及目录操作 `mkdir`、`rmdir`、`unlink`、`rename`；
- EXT4 核心特性：Extent 连续块管理与 JBD2 完整日志（事务管理、日志刷盘、全量崩溃恢复）；
- 强一致性原语：`fsync`、`fdatasync` 与设备 flush，语义与 Linux 等价；
- 两类 I/O 路径：绕过页缓存的 O_DIRECT 直接 I/O，以及经由 Asterinas PageCache 的缓冲 I/O 与 mmap；
- 标准化设备接口：经由 virtio-blk 访问块设备，在 QEMU/KVM 环境中可与 Linux 发行版 EXT4 同口径对照。

使用上需要预先了解一点：本系统的若干行为由 Asterinas 的启动参数（boot arguments，下文称 `ext4fs.*` 参数）控制，例如是否启用页缓存。不同的工作负载对应不同的推荐配置，第 4 节给出完整参数表与典型组合。

## 2. 运行环境要求

| 项 | 要求与说明 |
|---|---|
| 宿主操作系统 | Linux；开发与测试参考环境为 Ubuntu 24.04.1、内核 6.8.0-41 |
| 硬件虚拟化 | QEMU 8.2 与 KVM，宿主须存在 `/dev/kvm` 且当前用户有访问权限 |
| 容器镜像 | `asterinas/asterinas:0.17.0-20260227`，内含 Rust nightly、cargo-osdk 0.17、QEMU、e2fsprogs 1.47 等全部工具链 |
| 块设备接口 | virtio-blk（赛题规定的标准化接口） |
| 磁盘格式 | 测试镜像由 `mkfs.ext4 -b 4096` 创建，块大小 4 KiB |

宿主侧只需具备 Docker 与可用的 KVM；Rust 工具链、QEMU、e2fsprogs 等均由容器镜像提供，无需在宿主单独安装。若仅做本机源码开发而不进入容器，可执行 `tools/setup_dev_env.sh` 安装 `rust-src`、`rustfmt`、`rustc-dev`、`llvm-tools`、内核 target 与 VDSO；追加 `--no-vdso` 则只补齐组件而不安装 VDSO。

## 3. 获取与构建

### 3.1 进入开发容器

推荐在容器内进行构建与测试，以获得与参考环境一致的工具链版本：

```bash
docker run -it --privileged --network=host --device=/dev/kvm -v /dev:/dev \
  -v $(pwd)/asterinas:/root/asterinas \
  asterinas/asterinas:0.17.0-20260227
```

其中 `--privileged` 与 `--device=/dev/kvm` 使容器可使用 KVM 加速，`-v $(pwd)/asterinas:/root/asterinas` 把宿主仓库挂载进容器，从而在容器内的改动与宿主同步。

### 3.2 本机生成物与可重建资产

下列目录为本机生成物，不纳入版本控制，克隆仓库后可按需重建，使用者通常无需手动干预：

| 目录 | 内容与重建方式 |
|---|---|
| `target_lby/`、`.target_bench/` | 构建产物，由构建过程生成 |
| `benchmark/logs/` | 本地运行产物（已 gitignore）；需要版本化保存的证据用 `git add -f` 强制纳入 |
| `.local/linux_vdso`、`.local/xfstests-*` | VDSO 与 xfstests 预构建；缺失时运行 `tools/ext4/prepare_xfstests_prebuilt.sh` 重建 |
| `.cache/linux_binary_cache/vmlinuz` | fio 对照侧使用的 Linux 内核镜像；缺失时由 `prepare_host.sh` 自动下载，离线环境需手工预置同名文件 |

仓库已跟踪可复用的 initramfs（`benchmark/assets/initramfs/`），测试 runner 会按需重新打包，因此首次运行可能比后续略慢。

## 4. 挂载与配置

文件系统挂载于 virtio-blk 设备（在 guest 内表现为 `/dev/vda`），各功能与性能脚本会自动准备磁盘镜像、设置启动参数并拉起 QEMU，使用者一般通过环境变量间接配置，而非手工编辑启动命令行。

### 4.1 运行时参数（`ext4fs.*`）

| 参数 | 默认 | 含义 | 调整时机 |
|---|---|---|---|
| `ext4fs.page_cache` | 关 | 启用经 PageCache 的缓冲 I/O 与 mmap 路径 | 缓冲读写、mmap、SQLite 等真实应用须开启；纯 O_DIRECT 守底保持关闭 |
| `ext4fs.extent_map_cache` | 开 | 启用逻辑到物理的 Extent 映射缓存 | 常驻开启的性能优化项，通常无需调整 |
| `ext4fs.direct_read_cache` | 开 | 自研投机数据读缓存（已退役） | **诚实口径性能测试必须显式关闭**，详见第 8 节 |
| `ext4fs.phase2_profile` | 关 | 启用 FS / virtio / 锁 / JBD2 四层 ns 级延迟 profiling | 仅在做性能归因分析时开启，会引入额外开销 |

### 4.2 环境变量映射

测试脚本把上述参数暴露为环境变量，便于在命令行控制：`EXT4_PAGE_CACHE`、`EXT4_DIRECT_READ_CACHE`、`EXT4_EXTENT_MAP_CACHE` 分别对应同名参数，`LOG_LEVEL` 控制 guest 日志级别（性能测试建议设为 `error`，以避免串口日志干扰计时）。

### 4.3 典型配置组合

| 场景 | 推荐配置 | 理由 |
|---|---|---|
| O_DIRECT 守底（诚实口径） | `EXT4_DIRECT_READ_CACHE=0 EXT4_PAGE_CACHE=0 LOG_LEVEL=error` | 关闭投机缓存与页缓存，测纯设备直达路径 |
| 缓冲 I/O 与真实应用（SQLite） | `EXT4_PAGE_CACHE=1 EXT4_DIRECT_READ_CACHE=0 LOG_LEVEL=error` | 缓冲路径需页缓存；仍关闭投机缓存以保持诚实口径 |
| 性能归因分析 | 在上述基础追加 `ext4fs.phase2_profile=1` | 产出四层占比表，定位瓶颈 |

## 5. 支持的操作与边界

下表给出当前支持的 POSIX 操作及其验证来源；未列出的高级接口（如扩展属性、配额）不在当前范围。

| 类别 | 接口 |
|---|---|
| 文件 | `create` / `open` / `close` / `read` / `write` / `lseek` / `stat` / `fstat` / `truncate` / `ftruncate` |
| 目录 | `mkdir` / `rmdir` / `opendir` / `readdir` / `unlink` / `rename` |
| 持久化 | `fsync` / `fdatasync`、设备 flush |
| 内存映射 | `mmap`（读写映射与 writeback） |
| 直接 I/O | `O_DIRECT` 读写 |

**已知未实现或受限**：硬链接（hardlink）与符号链接（symlink）尚未实现，official xfstests 中相关用例不支持；ENOSPC 后的半成品元数据回滚、孤儿文件清理的异步化仍在完善；JBD2 撤销记录尚未写盘，构成一个特定的崩溃一致性边界。详见第 9 节与《架构设计文档》第 11 节。

## 6. 运行功能测试

功能测试以 `tools/ext4/run_phase4_in_docker.sh` 为统一入口，通过 `PHASE4_DOCKER_MODE` 选择套件。典型调用：

```bash
PHASE4_DOCKER_MODE=<mode> ENABLE_KVM=1 BENCH_ENABLE_KVM=1 \
  BENCH_ASTER_NETDEV=tap BENCH_ASTER_VHOST=on bash tools/ext4/run_phase4_in_docker.sh
```

可选的 `<mode>` 及其覆盖内容：

| `PHASE4_DOCKER_MODE` | 覆盖内容 |
|---|---|
| `crash_only` | JBD2 崩溃恢复矩阵（提交/检查点前后注入掉电并重放校验） |
| `phase6_with_guard` | Phase 6 功能套件与守底回归的组合 |
| `concurrency` | 标准 xfstests 并发套件（fsstress 多进程、崩溃恢复、并发直接 I/O） |
| `jbd_phase1` | JBD2 事务、刷盘与恢复基线 |
| `jbd_phase2_concurrency` | 自研多文件并发的数据完整性校验 |
| `jbd_phase3_host_crash` | host-crash 场景下的 fsync 持久化 |
| `jbd_phase3_fsync_flush` | fsync/fdatasync/flush 语义 |

**结果判定**。单个 xfstests 用例以日志中出现 `xfstests case done: <case> rc=0` 为通过，整体以 `All syscall tests passed.` 为通过；崩溃矩阵以末尾 `Crash summary` 表全部 PASS 为通过。

## 7. 运行性能测试

### 7.1 fio O_DIRECT 顺序读写守底（单线程，诚实口径）

```bash
EXT4_DIRECT_READ_CACHE=0 EXT4_PAGE_CACHE=0 LOG_LEVEL=error BENCH_ENABLE_KVM=1 \
  BENCH_ASTER_NETDEV=tap BENCH_ASTER_VHOST=on \
  bash test/initramfs/src/benchmark/fio/run_ext4_summary.sh
```

该入口对一组块大小（4K–1M）逐档测量顺序读写带宽，并与同口径的 Linux 对照计算比值。

### 7.2 fio 参数广度测试

```bash
bash test/initramfs/src/benchmark/fio/run_parameter_sweep_summary.sh
# SWEEP_GROUPS=F 只跑并发组；RUN_G_CORRECTNESS=0 跳过附带的正确性回归
```

该入口覆盖块大小、线程数、direct/buffered、是否插入 fsync 等维度的组合，用于定位瓶颈与并发可扩展性。

### 7.3 SQLite 真实应用

```bash
FS_LIST=ext4 PAGE_CACHE_LIST=1 LOG_LEVEL=error \
  bash test/initramfs/src/benchmark/sqlite/run_sqlite_summary.sh
# FS_LIST="ext4 ext2 ramfs" 可同时跑三文件系统的诊断三角
```

`FS_LIST` 同时包含 ext4、ext2、ramfs 时，可得到第 8 节所述的三文件系统对照，用于区分文件系统写路径成本与平台 I/O 地板。

### 7.4 理解 fio 命令骨架

各 fio 入口最终展开为如下骨架，便于使用者理解参数含义：

```bash
fio -rw={read|write} -filename={/ext4/fio-test | /dev/vda} \
    -size=1G -bs=<块大小> -numjobs=<线程数> -ioengine=sync \
    -direct=<0|1> [-fsync=<N>] -fsync_on_close=1 \
    -time_based=1 -ramp_time=60 -runtime=100
```

## 8. 性能口径与复现说明

性能数据的可信度取决于口径的一致与诚实，本系统在这一点上有明确规定，使用者复现时须一并遵循。

**公平对照**。Asterinas 与 Linux EXT4 在同一容器、同一 QEMU/KVM、同一块设备、同一轮次中交替运行；每个测试项执行前清空宿主页缓存（drop_caches），避免宿主缓存对结果的污染；guest 日志降到 `error`，避免串口 I/O 干扰计时。

**诚实口径**。所有用于性能宣称的测试一律关闭自研投机数据读缓存（`ext4fs.direct_read_cache=0`），fio 取 `direct=1`、`numjobs=1` 的中位数。历史上在投机缓存开启时得到的 read 127% / write 39% 已被废弃，不作为成绩使用。

**比值定义**。fio 比值为 Asterinas 带宽除以 Linux 带宽；SQLite 比值为 Linux 耗时除以 Asterinas 耗时。

仓库根目录的 `benchmark.md` 是 benchmark 与复现的权威指引（§0 给出最新结果快照，§1 给出环境准备与快速复现，§4/§6 给出各项精确跑法）；fio 参数 sweep 的完整证据见 `fio_direct_parameter_sweep_report_phase6.md`，SQLite 见 `sqlite_benchmark_report.md` 与 `technical_report.md` 第 7 节。

## 9. 已知限制

| 限制 | 说明与影响 |
|---|---|
| JBD2 撤销记录未写盘 | "元数据块释放后被复用为数据、且在检查点前崩溃"的窗口理论上存在数据覆盖风险；该窗口在当前 guest-crash 测试矩阵中不被触发，列入后续 hardening |
| hardlink / symlink 未实现 | official xfstests 相关用例不支持 |
| 空间回收待完善 | ENOSPC 半成品元数据回滚、孤儿文件清理需异步化，避免阻塞文件关闭路径 |
| official xfstests 全量未跑通 | 全量运行会在个别用例中断（堆分配错误、或 mmap 开页缓存触发更底层崩溃），已隔离待修 |
| host 掉电依赖假设 | 崩溃恢复对 host 掉电的保证依赖 virtio 同步写完成即有序持久化的假设；guest 崩溃为全覆盖 |
| `page_cache=0` 旧向量路径 | 在边界场景下已知会损坏；真实应用须使用 `page_cache=1`，守底使用 O_DIRECT |

## 10. 故障排查

| 现象 | 处置 |
|---|---|
| `Could not set up host forwarding rule` | QEMU hostfwd 随机端口偶发碰撞，重跑该模式即可；崩溃 runner 已加场景间隔缓解 |
| 依赖下载超时 | 设置代理后重试：`export http_proxy=… https_proxy=… all_proxy=socks5://127.0.0.1:7890` |
| 缺少 VDSO 或 xfstests 预构建 | 运行 `tools/ext4/prepare_xfstests_prebuilt.sh` 或 `tools/setup_dev_env.sh` 重建 |
| 缺少 Linux 对照内核 | `prepare_host.sh` 会自动下载 `vmlinuz`，离线环境手工预置同名文件 |
| 需在宿主直接运行以排障 | 统一环境：`CARGO_TARGET_DIR=$(pwd)/target_lby VDSO_LIBRARY_DIR=$(pwd)/.local/linux_vdso BOOT_METHOD=qemu-direct OVMF=off RELEASE_LTO=1 CONSOLE=ttyS0` |
