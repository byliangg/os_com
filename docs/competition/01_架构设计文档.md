# 架构设计文档：面向 RustOS 的高性能强一致性 EXT4 文件系统

**项目**：在 Rust framekernel 操作系统 Asterinas（OSTD 非特权运行环境，兼容 Linux ABI）之上，以 Rust 实现兼容 POSIX、支持 Extent 与 JBD2 完整日志的 EXT4 文件系统。
**代码基线**：分支 `feature-sqlite-phase-6`。集成层 `kernel/src/fs/ext4/` 约 6.9k 行，核心库 `kernel/libs/ext4_rs/` 约 15.5k 行。
**文档定位**：本文给出系统的总体架构、分层依据、模块职责、关键数据结构、日志子系统、并发模型、缓存体系、数据路径与崩溃一致性语义，并对每一处非平凡的设计选择给出动机与代价分析。性能优化技术的量化论证另见《性能优化技术研究报告》，功能与崩溃恢复的验证证据另见《测试文档》。

## 1. 引言

### 1.1 问题背景

文件系统在崩溃一致性与性能之间长期存在结构性张力。为了在掉电或宕机后仍能把磁盘恢复到一个自洽状态，主流 EXT4 采用 JBD2（Journaling Block Device, 第 2 版）日志：所有元数据更新在落到其最终位置（home location）之前，先以事务的形式顺序写入一段连续的日志区，待事务的提交记录（commit record）安全落盘后，才允许把元数据回写到 home。这一机制以"先写日志、再写数据"的次序约束换取崩溃可恢复性，但其代价是元数据 I/O 被放大、并被强加了顺序依赖，进而与追求吞吐和低延迟的目标相冲突。工业界与学术界普遍将这一现象概括为"安全一致性与高性能"的核心矛盾。

与此并行的是内存安全问题。传统操作系统与文件系统以 C 语言为主，手动内存管理使缓冲区溢出、悬垂指针、释放后使用等缺陷长期存在，业界估计相当比例的系统级安全漏洞由此而来。文件系统作为内核中代码量最大、与不可信磁盘数据直接交互的子系统之一，是这类缺陷的高发区。

### 1.2 平台特性与研究契机

Asterinas 是基于 Rust 的 framekernel 操作系统。其设计将可信计算基（Trusted Computing Base, TCB）压缩到一个被称为 OSTD 的最小框架内，框架之上的内核服务运行于受约束的、非特权的执行环境，依靠 Rust 的所有权与借用语义在编译期消解大量内存安全风险，同时在系统调用 ABI 层与 Linux 兼容。Asterinas 此前并不支持 EXT4 等主流磁盘文件系统，这既限制了它在数据密集与云原生场景的可用性，也意味着一片尚未被探索的设计空间：framekernel 的非特权运行环境与 Rust 的静态保证，是否可以在不牺牲一致性的前提下，为文件系统的性能优化提供新的结构边界。

本项目即在这一背景下展开。其工程目标是在 Asterinas 上交付一个功能完整、强一致、性能接近 Linux 的 Rust EXT4；其研究目标是检验"在 framekernel 架构下，能否在保持 JBD2 完整语义的同时把性能逼近 C 版 EXT4"，并由此提炼面向 RustOS 的、可迁移的存储层优化方法。

### 1.3 设计目标

系统的设计目标由赛题任务直接导出，可归纳为六个相互制约的维度。

- **POSIX 兼容**：覆盖 `create/open/close/read/write/lseek/stat/truncate/mkdir/rmdir/unlink/rename` 等文件与目录操作核心接口，使既有应用无需修改即可运行。
- **EXT4 核心特性**：实现 Extent 连续块管理与 JBD2 完整日志，后者须涵盖日志记录、事务管理、日志刷盘与全量崩溃恢复。
- **强一致性**：`fsync`、`fdatasync` 与设备 flush 须与 Linux 的持久化语义等价，多场景掉电恢复后数据一致。
- **并发**：多文件并发读写不得出现数据错乱或丢失。
- **性能**：I/O 吞吐与延迟须接近 Linux 发行版 EXT4。
- **安全**：以 Rust 所有权语义规避内存安全缺陷，并运行于 OSTD 非特权环境。

这些目标并非彼此独立。强一致性约束（日志次序、提交屏障）与性能目标直接对立；并发目标要求放松串行化，又会扩大一致性推理的难度；运行于非特权环境则限制了某些传统内核可用的优化手段。架构设计的核心任务，正是在这些约束之间寻找一个可被验证、可被解释的平衡点。

### 1.4 约束条件

测试与部署环境对设计施加了若干硬约束。其一，存储设备统一经由 virtio-blk 虚拟块接口访问，这是赛题规定的标准化接口，也意味着设备往返延迟由该接口的实现决定，文件系统层无法绕过。其二，性能评估在 QEMU/KVM 标准化环境中与 Linux 发行版 EXT4 同口径对照。其三，Asterinas 不提供 device-mapper 支持，因此 xfstests 中依赖 `dm-log-writes`、`dm-flakey` 的崩溃注入用例无法直接运行，需由自研的崩溃注入场景在等价的语义点上补位。这些约束在后文相应章节会被反复引用。

## 2. 总体架构

### 2.1 分层依据

系统在纵向上划分为**集成层**与**核心库**两个层次。这一划分并非单纯出于工程整洁性，而是由两类关注点的本质差异决定的。

磁盘格式的编解码、Extent 树的维护、块与 inode 的分配、以及日志的记录与重放，是一组**与具体内核无关**的逻辑：它们只依赖块设备提供的"读一块、写一块"抽象，原则上既可在用户态 FUSE 进程中运行，也可在内核态运行。将这部分逻辑沉淀于 `kernel/libs/ext4_rs/`（下称核心库），其价值在于磁盘兼容性可以独立于内核演进而被验证——例如借助宿主机的 e2fsprogs 与 debugfs 对同一镜像做互操作核对。

与之相对，VFS 语义的实现、页缓存的协同、并发可见性的维护、以及 bio 的合成与提交，则**强绑定于 Asterinas 的运行时模型**：它们依赖 OSTD 提供的同步原语、Vmo 内存对象、PageCache 基础设施与块层接口。将这部分收敛于 `kernel/src/fs/ext4/`（下称集成层），使一致性与并发的推理被限制在一个有界的代码面内，便于审查与回归。

这一划分带来的代价是每次操作需要在两层之间传递数据与上下文，存在一定的拷贝与 clone 开销；该开销在性能分析中被显式计入，并通过缓存与批量化加以摊薄（详见《性能优化技术研究报告》）。

### 2.2 层次结构

自顶向下，系统的运行时栈如下：

```text
┌──────────────────────────────────────────────────────────────┐
│ 用户态负载   fio (direct=1)  │  SQLite speedtest1  │ xfstests   │
├──────────────────────────────────────────────────────────────┤
│ Asterinas VFS / syscall      read/write/fsync/rename/mmap …    │
│   通用 PageCache + Vmo（缓冲 I/O、mmap、writeback 的承载）       │
├──────────────────────────────────────────────────────────────┤
│ 集成层  kernel/src/fs/ext4/  （约 6.9k 行）                    │
│   Ext4Inode (inode.rs)  ：O_DIRECT 与缓冲路径分流、VFS 接口     │
│   Ext4Fs   (fs.rs)      ：缓存体系、锁表、JBD2 事务驱动、        │
│                           PageCacheBackend、DeviceBlockCache、  │
│                           fsync 刷盘编排                         │
├──────────────────────────────────────────────────────────────┤
│ 核心库  kernel/libs/ext4_rs/  （约 15.5k 行）                 │
│   ext4_defs ：on-disk 结构（super_block/inode/extents/…）       │
│   ext4_impls：file/dir/balloc/ialloc/extents/inode             │
│   jbd2      ：journal/transaction/handle/commit/checkpoint/    │
│               recovery/device/space/superblock                 │
│   alloc_guard：单次操作分配块集合                               │
├──────────────────────────────────────────────────────────────┤
│ 块层        bio / BioSegment / BioWaiter                       │
│ virtio-blk  （同步完成语义）→ QEMU/KVM 磁盘                    │
└──────────────────────────────────────────────────────────────┘
```

集成层与核心库之间的接口是一个"取 `Ext4` 实例、在其上执行一次受日志保护的操作、提交或回滚"的事务化调用约定，集中体现为集成层的 `run_journaled_ext4` 收敛点（chokepoint）。所有会修改元数据的路径都必须经由该点进入核心库，这一约束是后文缓存失效协议与锁序得以成立的前提。

### 2.3 控制流与数据流概览

读路径与写路径在结构上并不对称。只读操作（`read`、`stat`、`lookup`）不进入 `run_journaled_ext4`，因而不持有全局日志锁，只在 per-inode 共享锁与 `inner` 锁的保护下完成映射查询与设备读取；这是并发读得以与写解耦的结构基础。写路径则进一步按是否需要分配而分叉：纯覆盖写在映射已存在且不越过文件尾时走免日志的快路径，仅置脏页缓存并延迟到 `fsync` 落盘；其余（追加、空洞填充、元数据变更）进入慢路径，在全局日志锁与一个 JBD2 handle 的保护下完成分配与元数据更新。`fsync` 则是把内存中的脏状态推进到持久化介质的唯一安全点，它串接页缓存写回、日志提交与设备 flush 三个阶段。三条路径的细节见第 8 节。

## 3. 模块分解

### 3.1 集成层 `kernel/src/fs/ext4/`

集成层由三个文件构成，但逻辑密度集中于 `fs.rs`。

`fs.rs` 实现 `Ext4Fs`，是整个文件系统在 Asterinas 中的运行时实体。它持有核心库的 `Ext4` 实例（包裹于 `inner: Mutex<Ext4>`）、JBD2 运行时与日志状态、per-inode/per-dir 的正确性锁表、若干性能缓存，以及连接 Asterinas PageCache 的后端回调（`PageCacheBackend` 的 `read_page_async`/`write_page_async`）。所有受日志保护的操作经由 `run_journaled_ext4` 进入，fsync 的三段刷盘链、O_DIRECT 读写路径与设备块缓存 `DeviceBlockCache` 亦定义于此。

`inode.rs` 实现 `Ext4Inode`，即 VFS `Inode` trait 的承载。它负责 O_DIRECT 与缓冲路径的分流、`fsync`/`fdatasync` 的入口、以及 `lookup`、创建、删除、`rename` 等名字空间操作。该层的一个已知设计弱点是 inode 在内存中保留了一个字符串形式的 `path` 字段并以之解析 `..`，在祖先目录被改名后可能产生过期解析（详见第 11 节）。

`mod.rs` 负责模块装配、挂载入口与启动参数（`ext4fs.*`）的解析，将运行时配置（页缓存开关、各类缓存开关、profiling 开关）注入 `Ext4Fs`。

### 3.2 核心库 `kernel/libs/ext4_rs/`

核心库在结构上分为定义（`ext4_defs`）、实现（`ext4_impls`）、日志（`jbd2`）与工具（`utils`）四组。

`ext4_defs` 给出 on-disk 结构的内存镜像与编解码：超级块、块组描述符、inode、Extent 头与索引/叶项、目录项、以及 JBD2 的各类块头（描述符块、提交块、撤销块）。这一组代码刻意只描述"磁盘上是什么"，不含任何 I/O 或并发逻辑，从而可被宿主工具链直接核对。

`ext4_impls` 给出操作语义。`file.rs` 承载文件读写、`prepare_write_at` 的分配准备、`ensure_write_range_mapped` 的逐块映射建立、物理预分配以及 unwritten extent 的写时转换；`extents.rs` 实现 Extent 树的查找、插入（含左合并以保持树紧凑）与删除，并对叶节点容量施加边界钳制，遇到结构损坏时降级为 EIO 而非 panic；`balloc.rs` 与 `ialloc.rs` 分别管理块位图与 inode 位图分配；`dir.rs` 处理目录项的增删查与 `..` 解析；`inode.rs` 处理 inode 自身的读写与链接计数；`alloc_guard.rs` 提供 `OperationAllocGuard`，记录单次操作内已分配的块集合以避免重复分配。

`jbd2` 是日志子系统的实现，其内部结构与职责见第 5 节。`utils` 提供 CRC32C、位图、路径与错误码等基础设施。

### 3.3 与平台其他子系统的接口

为接入持久化与内存映射，集成层与 Asterinas 的块层、PageCache 与 VFS 三处发生交互，但改动以 ext4 自身为主、边界清晰。块层提供 bio/BioSegment/BioWaiter 抽象，集成层在 O_DIRECT 与批量写回路径上将连续映射合成大 bio 后提交；PageCache 提供 Vmo 承载的页缓存，集成层通过后端回调把"读某页/写某页"翻译为对核心库的调用；VFS 则通过 `Inode`/`FileSystem` trait 驱动整个文件系统。

## 4. 磁盘结构与 Extent 管理

系统遵循标准 EXT4 的盘上布局，文件系统由 `mkfs.ext4 -b 4096` 创建，块大小固定为 4 KiB。超级块与块组描述符表描述全局几何，inode 为标准 256 字节，其 `i_block` 区在 Extent 文件中承载 Extent 树根，以魔数 `0xF30A` 标识。

采用 Extent 而非传统间接块的动机是降低大文件映射的元数据开销。间接块以"每个逻辑块一个物理块号"的方式存储映射，对连续大文件会产生与文件大小成正比的指针数量；Extent 则以三元组（起始逻辑块、长度、起始物理块）描述一段连续映射，使连续文件的映射元数据近似为常数。Extent 以树组织，叶节点存放实际 extent 项，内部节点存放索引；在 extent 数目处于数百量级时，树通常只有一到两层，单次逻辑到物理的映射查询（`ext4_map_blocks`）只需有限次的树下沉。插入（`insert_extent`）在新区间与相邻 extent 物理连续时执行左合并，避免树因碎片化而膨胀；删除（`ext_remove_leaf`）在收缩文件时回收 extent。

在基础 Extent 之上，系统引入了 **unwritten extent** 语义以支持物理预分配。预分配但尚未写入实际数据的块被标记为 unwritten：读路径对这类区间返回零，写路径在事务内通过 `convert_unwritten_span` 将其原子地转换为 written 并在可能时执行左合并。该机制使分配可以提前、批量地进行，又不会在崩溃后把未初始化的磁盘内容当作有效数据暴露给应用——崩溃后多出的、位于文件尾之外的已分配块至多构成空间泄漏，读请求被 inode 大小钳住而不会触及它们。这一语义与 Linux 对 `fallocate` 的处理一致。

健壮性方面，`extents.rs` 对叶节点容量做边界检查，当遇到越界或自相矛盾的节点时返回 EIO 并使相关操作失败，而不是以 panic 终止整机。这一选择源于内核环境的现实约束：文件系统直接消费来自磁盘的、可能已损坏的字节，任何对结构完整性的隐含假设都必须以显式检查兜底。

## 5. JBD2 日志子系统

### 5.1 设计取舍：全块镜像与 ordered 模式

日志子系统在两个基本维度上做出了取舍，二者共同决定了它的复杂度与行为。

其一是日志的粒度。标准 JBD2 可以记录块级的物理日志；本实现采用**全块镜像**：当一个元数据块被修改时，其整块的最新内容以镜像形式留存于内存中的当前事务，而对 home 位置的实际写入被推迟到检查点（checkpoint）。这一选择使提交与重放的逻辑直观——重放即"把镜像逐块写回 home"，但代价是日志放大，因为即便只改动块内若干字节也要记录整块。放大效应由两个机制抑制：提交存在一个按修改块数（达到 128 块）触发的批量阈值，使多次小改动可合并到一次提交；检查点在事务深度或日志空间触及水位时批量回写 home 并推进日志尾，回收空间。

其二是数据块的处理模式。本实现采用 **ordered 模式**：文件数据块不进入日志，而由写路径直接写到其 home 位置；日志只保护元数据。ordered 模式天然满足"数据先于提交记录落盘"这一崩溃一致性的关键次序——因为数据走的是 home 直写，而元数据的可见性由提交记录把关。其代价是不能像 data-journal 模式那样为数据本身提供原子性，但这对绝大多数工作负载是可接受的折中，也是 Linux EXT4 的默认模式。

在 active handle 存在期间，被推迟的 home 写意味着磁盘上的元数据可能滞后于内存事务。为使读路径看到一致的最新视图，系统在读元数据时通过 `overlay_metadata_read` 把内存中的最新镜像叠加到从磁盘读出的内容之上，从而对上层呈现"仿佛已经写回"的语义。

### 5.2 事务生命周期

一次事务经历"运行—锁定—提交—检查点"四个阶段：

```text
[*] ──start_handle（按操作估算 credits）──▶ Running
Running ──record_metadata_write（全块镜像入内存，home 写延迟）──▶ Running
Running ──最后一个 handle stop / credits 超 1024 软限触发轮转──▶ Locked
Locked  ──prepare_commit（修改块数 ≥128 批量阈值，或 fsync 强制）──▶ Commit
Commit  ──write_commit_plan：descriptor + payload → sync 屏障
           → commit block → 更新 journal 超级块──▶ Checkpoint 列表
Checkpoint 列表 ──事务深度 ≥64 或日志空间触及低水位：批量写回 home
                  → sync → 推进日志尾──▶ [*]
```

每个文件系统操作在进入慢路径时通过 `start_handle` 开启一个 handle，并按操作类型估算其所需的 credits（日志空间额度）。credits 在本实现中是软限制：它只影响事务何时轮转的启发式判断，而不强制拒绝超额操作。这一设计简化了准入逻辑，但带来一个边角风险——当单个事务的元数据块数超过日志可用空间时，提交会失败并把事务塞回重试，构成潜在活锁（详见第 11 节 C6）。

### 5.3 提交屏障与崩溃恢复

提交的正确性依赖屏障纪律。`write_commit_plan` 在写出提交块之前，先写描述符块与负载块，再发起一次 `block_device.sync()` 设备屏障，确保描述符与负载在提交块之前持久化；提交块落盘后再更新日志超级块。`fsync` 路径在其尾部还有一次最终的设备 flush。由此，"提交记录在盘上即意味着该事务完整且其数据已在 home"这一不变量成立，重放据此判定事务边界。

挂载时，`recovery` 扫描日志区，定位最后一个完整提交的事务，对其后所有已提交事务逐块重放镜像，随后重置日志。重放是幂等的——同一镜像写回 home 多次结果相同——因此在重放过程中再次崩溃不会破坏一致性。

### 5.4 已知边界：撤销（revoke）记录尚未写盘

标准 JBD2 用**撤销记录（revoke record）**处理一类特定的危险序列：某元数据块 B 的镜像存在于一个已提交事务 T 中，其后 B 被释放并被重新分配为数据块、由写路径直写了用户数据；若在 B 经检查点回写之前崩溃，重放会把 T 中 B 的过期元数据镜像写回，从而覆盖已经写入的用户数据。撤销记录的作用是声明"某块在某序列号之后不应再被重放"，重放时据此跳过。

本实现的提交路径目前只写描述符、负载与提交三类块，尚未把撤销记录写入日志；`RevokeBlockHeader` 仅在恢复侧被读取，写侧无调用。集成层的 `revoke_jbd2_checkpoint_metadata_blocks` 只是该问题的内存半边补丁，且仅清理检查点列表。因此上述危险序列在理论上仍有数据覆盖风险。需要明确的是，这一风险在当前崩溃测试矩阵覆盖的 guest-crash 场景中并未被触发，因为这些场景没有构造"元数据块释放后被数据复用且在检查点前崩溃"的精确时序；但"测试全绿"不等于"不存在覆盖洞"。本文据实将其列为待补的崩溃一致性边界，对应的完整修复需要在释放元数据块的操作中记录撤销集合、在提交时写出撤销块，并在重放时引入按序列号的过滤（避免把块后来又合法地成为元数据并再次记录的新镜像一并跳过）。该项被列入后续 hardening，验证实验设计见《测试文档》附录 A-1。

## 6. 并发模型

### 6.1 从全局串行到 per-inode 粒度

本实现所基于的开源 ext4_rs 依赖一个全局的运行时块大小状态，这一全局可变状态在语义上要求所有受其影响的操作串行执行，构成并发的根本障碍。架构上的第一步是移除该全局状态，把块大小等运行时信息下沉为操作局部的上下文，从而解除"所有 journaled 操作必须串行"的隐含约束。在此基础上，系统建立了按对象粒度的并发模型，使不相关的 inode 与目录上的操作可以并行推进。

### 6.2 锁全景

| 锁 | 保护对象 | 关键性质 |
|---|---|---|
| `EXT4_RS_RUNTIME_LOCK`（全局 Mutex） | 全部受日志保护的变更操作 | 仅在 `run_journaled_ext4` 内持有；只读路径不持有 |
| `inner: Mutex<Ext4>` | `Ext4` 实例（每次操作 clone 的源） | 只读路径在此锁下横跨设备 I/O，是并发读的首个序列化点 |
| per-inode 正确性锁（RwMutex） | 单文件读写、fsync、truncate | 见 6.4 的共享/独占划分 |
| per-dir 正确性锁（RwMutex） | 目录操作 | 持锁点均为独占，语义与互斥等价 |
| `jbd2_runtime: RwMutex` | 事务状态机、overlay 读 | |
| `jbd2_journal` + `jbd2_checkpoint_lock` | 日志盘上空间、检查点串行 | |

### 6.3 锁序与死锁论证

为避免循环等待，系统规定唯一的获取顺序：`inode/dir 锁 → RUNTIME_LOCK → inner → jbd2_runtime/jbd2_journal`。涉及多个 inode 的操作（如 `rename` 跨目录）按 inode 号排序后依次获取对象锁，从而消除 ABBA 型的循环等待。在该顺序下，对现有代码路径的审查未发现可达的死锁环路。需要指出的是，这一无死锁性依赖一条隐含前提："页缓存后端回调（`read/write_page_async` 进而调用核心库）不会在已持有 `RUNTIME_LOCK` 时被进入"。该前提目前成立，但它没有被断言固定下来，一旦后续重构把 `page_cache.write` 移入受日志保护的闭包内，便会构成自死锁。第 11 节将其列为结构性脆弱点 C7-d。

### 6.4 共享锁直接 I/O：对齐 Linux 的覆盖写并发

per-inode/per-dir 正确性锁最初实现为互斥锁，这意味着同一文件上的并发读写完全互斥，且持锁区间横跨设备等待，导致单文件多线程吞吐被锁封顶（实测在约 2800 MB/s 处停滞）。Linux EXT4 在此处的做法是：对已分配区间的纯覆盖直接 I/O 写，只需持有共享的 `i_rwsem`，从而允许与读、以及彼此并行。

本系统据此把正确性锁由互斥锁升级为读写锁，并在 `page_cache=0` 配置下让经过映射验证的纯覆盖 O_DIRECT 写在**共享锁**内完成"是否为纯覆盖"的判定与提交，O_DIRECT 读同样持共享锁；而任何会改变映射的操作（分配、truncate、rename）持**独占锁**。这里的 TOCTOU 安全性由一个不变量保证：判定为"纯覆盖"所依据的映射，只可能被持独占锁的一方改变，而独占锁与共享锁互斥，因此在共享锁持有期间映射不会被并发地置换。该改造在不放松一致性的前提下拆除了单文件并发墙，使并发写随线程数近似线性扩展。

## 7. 缓存体系

### 7.1 失效协议是核心关注点

集成层维护多套缓存以摊薄 per-op 固定开销，但缓存的难点不在命中而在失效。系统把失效统一锚定在 `run_journaled_ext4` 这一变更收敛点上，并以**生成数（generation counter）**防止 TOCTOU：读出缓存项时记录当时的生成数，使用前再次校验，若中途发生过变更收敛则判定失效。这一设计的好处是失效逻辑集中、易于审查；代价是部分缓存采用了较粗的整体清除粒度（例如目录操作保守地清空目录项缓存），在写密集场景下会损失一部分命中率，这一权衡在性能分析中被量化。

### 7.2 各缓存的职责

| 缓存 | 内容 | 作用与边界 |
|---|---|---|
| `inode_meta_cache`（含生成数） | stat 元数据 | 免重复读 inode 块；失效经收敛点单点清理 |
| atime/ctime/mtime 节流缓存 | 时间戳 | 支撑 relatime 语义，减少时间戳变更引发的日志 |
| `dir_entry_cache` | 目录项及其字节偏移 | 加速 lookup；当前无容量上界 |
| `inode_extent_map_cache` | 逻辑→物理映射 | 免重复 Extent 树下沉 |
| `DeviceBlockCache` | 设备 home 块内容的 write-through 镜像（约 32 MiB，LRU） | 使元数据块读命中内存；位于 JBD2 overlay 之下，故检查点/恢复写天然穿透，仅 O_DIRECT 数据 bio 需显式失效；实测命中率约 98.5% |
| `WrittenCoverage` | per-inode 已分配区间集 | 覆盖写快路径的判定结构，单次前驱查询即可判断区间是否已映射 |
| `inode_page_caches` | per-inode 页缓存状态 | 承载缓冲 I/O 与 mmap |
| `inode_direct_read_cache` | 已退役的投机数据读缓存 | 默认开启，但诚实口径测试全程关闭 |

关于最后一项需特别说明口径：自研投机数据读缓存默认开启，但本项目所有用于性能宣称的测试均主动关闭它；历史上"开启版"得到的 read 127% / write 39% 不再作为成绩使用。这一纪律贯穿《测试文档》与《性能优化技术研究报告》。

## 8. 关键数据路径

### 8.1 缓冲写：快路径与慢路径

缓冲写在取得 per-inode 锁并将用户数据拷入临时缓冲后，按是否需要改变映射分叉：

```text
write(fd, buf, len)
  ├─ 写区间末端 ≤ 当前文件大小，且区间已全部映射  → 覆盖写快路径：
  │     touch_mtime_ctime（受 relatime 节流，每秒至多一次日志）
  │     → page_cache.write 置脏页 → 返回（无 JBD2 handle）
  └─ 追加 / 空洞 / 越尾                            → 慢路径：
        run_journaled_ext4（全局日志锁 + JBD2 handle）
        → prepare_write_at 分配（物理预分配 + unwritten）
        → 在日志内更新 inode 大小（先于脏页）
        → page_cache.write 置脏页
```

慢路径中"先在日志内更新 inode 大小，再置脏页"的次序并非偶然，而是写回正确性所依赖的一条隐式不变量：脏页内容永远不超过当前盘上记录的 inode 大小，从而保证后续写回时不会把尚未被大小覆盖的字节当作有效数据落盘。该不变量在基线路径上恰好成立，但缺乏断言保护，是若干潜在风险的共同根源（第 11 节 C4、C7-a）。

### 8.2 fsync 持久化链

`fsync` 是把内存脏状态推进到介质的唯一安全点，它顺序经历三个阶段：

```text
fsync(fd)
  ① 页缓存写回：sync_page_cache_for_inode
       合并连续脏页区间 → write_pages_async（合并 handle 与 bio）
       evict_range（写回并标记 clean；保留 clean 页）
  ② 日志提交：fsync_regular_file → 依 inode 的目标事务号 force_commit
       写 descriptor + payload → sync 屏障 → commit block → 更新日志超级块
  ③ 设备屏障：block_device.sync()（最终落盘）
```

阶段①中"写回后保留 clean 页"是一项关键的性能修正（对应优化技术 T9）：早期实现会在写回后把整个文件的页（含未脏的 clean 页）一并丢弃，导致每次提交后文件缓存归零、后续读与部分页写的回填全部退化为对设备的逐 4 KiB 同步读，这正是真实应用写路径慢于无日志文件系统数十倍的首要原因。保留 clean 页使内存上界回落到工作集规模，与无日志文件系统同构。

### 8.3 直接 I/O 与缓冲的一致性协议

O_DIRECT 绕过页缓存直达设备，但必须与页缓存保持一致，否则会读到陈旧数据或丢失尚未写回的脏数据。系统采用与 Linux 同构的协议：

```text
O_DIRECT 写：取 inode 锁 → evict_page_cache_range（先把重叠脏页写回，对应 Linux 的 write-and-wait）
            → 已映射则复用映射 / 未映射则 journaled 准备 → 合成大 bio 提交
            → 成功后 discard_page_cache_range（失效重叠页，对应 Linux 的 invalidate）
O_DIRECT 读：取 inode 锁 → evict_page_cache_range（先刷脏页）→ 映射 → bio → 拷出
```

写前写回脏页、写后失效重叠页，使后续的缓冲读不会命中已被直接写覆盖的旧页；读前刷脏页使直接读不会漏掉尚在页缓存中的最新数据。残留的小边界（直接 I/O 与并发 mmap 写之间无额外防护）在 Linux 上同样存在，作为已知语义边界声明。

### 8.4 truncate 与 unlink

`truncate` 取 inode 锁后先把页缓存全量写回，再在日志保护下执行 `ext4_truncate`，随后丢弃缓存并调整大小；"先写回再丢弃"的次序保证不会把待写回的数据连同被截掉的范围一起丢失。`unlink` 在链接计数归零且无打开句柄时，于 `cleanup_unlinked` 中丢弃页缓存并在日志保护下把文件截断为零长度，回收其块。

## 9. 页缓存与内存映射

系统复用 Asterinas 通用的 PageCache 与 Vmo：每个常规文件 inode 对应一份页缓存状态，缓冲读写、mmap 与 writeback 均经此路径，而 O_DIRECT 绕过页缓存但通过第 8.3 节的协议与之保持一致。部分页写入会触发 `commit_page` 进而 `read_page_async` 的读—改—写回填，以补齐页内未被本次写覆盖的字节；整页对齐写则走 `commit_overwrite` 免去回填。mmap 写产生的脏页在 `fsync` 时一并写回，崩溃后可恢复（《测试文档》第 7 节给出 mmap 脏页 fsync 的验证）。需要指出，当前页缓存后端回调以同步方式完成并返回一个空的 BioWaiter，平台的预读状态机在本文件系统上退化为串行逐块读；在写侧瓶颈已消除后，缓冲读若成为瓶颈可再引入真正的异步批量回填（第 11 节 P6）。

## 10. 持久化与崩溃一致性语义

系统的崩溃一致性建立在两条屏障与一组明确声明的假设之上。提交块之前的设备 sync 屏障与 fsync 尾部的最终 flush 共同保证"提交记录落盘即事务完整"，这使 `fsync`/`fdatasync` 与设备 flush 达成与 Linux 等价的持久化语义（该结论在 Phase 3 的语义收口中得到验证）。

在恢复能力的范围上，本文采取主动声明的口径。对 **guest 崩溃**（虚拟机内的内核崩溃、进程被杀、模拟掉电），系统提供全覆盖保证：重新挂载后重放已提交事务，校验显示数据一致性达到 100%。对 **host 掉电**（物理机断电导致设备缓存丢失），一致性依赖一条更强的假设——virtio 同步写完成即意味着有序持久化；该假设在 guest 崩溃下无条件成立，在 host 掉电下则取决于底层设备是否真正在返回完成前落盘，因此答辩中须主动声明这一边界（与 Phase 3 文档一致）。此外，第 5.4 节的撤销记录缺口构成 guest 崩溃覆盖之内的一个特定窗口，已据实声明。

## 11. 设计权衡与已知边界

本节集中列出架构层面的权衡及其代价，以及尚未闭合的边界，以便审查者评估系统的成熟度。

**结构性权衡**。两层划分以少量跨层拷贝换取磁盘逻辑的可独立验证；全块镜像以日志放大换取提交与重放的简洁，由批量阈值与检查点抑制；ordered 模式以放弃数据原子性换取"数据先于提交"的天然成立；同步 virtio 完成语义以一条 host 掉电假设换取持久化推理的简化。这些权衡均有明确的代价侧，且代价侧都被纳入测试或声明。

**已知正确性边界**。其一，撤销记录未写盘（C1），并需配套按序列号过滤的重放（C2），二者必须一并修复。其二，受日志保护的操作若中途失败（如分配途中遇 ENOSPC），其已记录的半成品元数据镜像仍会随事务提交，缺少 handle abort 到 journal abort 的升级路径（C3）；保守的修复是在闭包返回错误时令文件系统转入只读以阻止不一致扩散。其三，第 8.1 节的"大小先于脏页"等四条不变量目前依赖"恰好成立"而非断言保护（C7），低成本的加固是为每条加入调试断言或计数。其四，inode 的内存 `path` 字段使 `..` 解析在祖先改名后可能过期（C5），正解是改为读取目录盘上真实的 `..` 项、身份只用 inode 号。其五，`page_cache=0` 的旧向量写路径在边界场景下已知会损坏，当前应用走 `page_cache=1`、守底走 O_DIRECT，建议后续直接删除该路径（C8）。其六，单事务超过日志容量时的提交—回退活锁（C6），可与 C3 共用只读降级机制兜底。

**性能侧的结构性上限**。真实应用（SQLite）的写性能受限于"对每 4 KiB 新分配写都同步支付分配与转换成本"的付税方式；要逼近 Linux 需引入延迟分配与后台回写，而后者的前置条件正是上述若干不变量的加固。该分析在《性能优化技术研究报告》中展开。

## 12. 结语

本系统以集成层与核心库的两层架构，在 Asterinas framekernel 上实现了功能完整的 EXT4：Extent 连续块管理、全量 POSIX 接口、JBD2 完整日志（事务管理、日志刷盘、全量崩溃恢复）、多文件并发读写、与 Linux 等价的 fsync/flush 持久化语义，以及页缓存与 mmap 集成。架构在分层依据、并发锁序、缓存失效协议与崩溃一致性范围上均给出了可被审查与声明的设计依据，并为后续的性能优化（缓存体系、unwritten extent、共享锁直接 I/O 等）提供了结构基础。系统当前存在的边界（撤销记录、失败操作的只读降级、若干隐式不变量的断言化、hardlink/symlink 等）已被据实列出，构成清晰的后续工作方向。
