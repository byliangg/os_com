# 测试文档：Asterinas EXT4 文件系统

**文档定位**：本文描述本 EXT4 文件系统的验证方法学、测试环境、用例组织与测试结果，覆盖功能正确性、崩溃一致性、并发正确性、持久化语义与性能五个层面，并据实声明尚未覆盖的部分与已知边界。验证所依据的设计假设见《架构设计文档》，性能口径与归因见《性能优化技术研究报告》。
**代码基线**：分支 `feature-sqlite-phase-6`。脚本入口与判定口径与《用户手册》第 6、7 节及仓库 `benchmark.md` 一致。

## 1. 验证目标与方法学

### 1.1 验证目标的分解

赛题要求"功能正确性遵循 xfstest 规范、性能使用 FIO 与 SQLite 等工具评估"。据此，本系统的验证被分解为四个相互独立又彼此印证的层面，分别对应赛题优秀档的不同评分项：

1. **功能正确性**——以 xfstests 规范用例为主、自研功能用例为辅，覆盖 POSIX 接口与 EXT4 特性，对应"实现完整度"与"功能正确性验证标准"；
2. **崩溃一致性**——验证 JBD2 的事务管理、日志刷盘与全量崩溃恢复，覆盖多场景掉电后的数据一致性，对应"全量崩溃恢复"与"多场景崩溃恢复测试，数据一致性 100%"；
3. **并发正确性**——验证多文件并发读写不出现数据错乱或丢失，对应"并发读写测试无数据错乱、丢失"；
4. **性能**——以 fio 合成负载与 SQLite 真实应用，在与 Linux 同口径的条件下评估吞吐与延迟，对应"性能指标"与"性能优化技术 ≥5% 提升"。

### 1.2 方法学原则

验证方法学有三条贯穿始终的原则，它们既保证结论可信，也约束了哪些数据可以被引用。

**公平对照**。所有对照实验在同一容器、同一 QEMU/KVM、同一 virtio 块设备、同一轮次中交替运行 Asterinas 与 Linux EXT4，并在每个测试项前清空宿主页缓存（drop_caches），使两侧面对相同的冷缓存初始条件。

**诚实口径**。性能数据一律在关闭自研投机数据读缓存（`ext4fs.direct_read_cache=0`）的条件下采集，fio 取 `direct=1`、`numjobs=1` 的中位数；投机缓存开启时得到的历史数据（read 127% / write 39%）被显式废弃，不作为任何结论的依据。这一纪律的意义在于：投机缓存会以牺牲某些一致性边界为代价放大读数，把它计入成绩会高估系统的真实能力。

**守底门控**。任何代码改动后必须重跑崩溃、并发、fsync 与 SQLite 完整性等守底套件，任一项相对既有基线回退即视为回归并止损。这把"优化不得以牺牲正确性为代价"从口号变成了可执行的门控。

需要预先声明一条方法学上的诚实限制：测试套件全部通过并不等同于不存在覆盖洞。本文第 11 节会据实指出当前崩溃矩阵尚未构造的特定时序，以及由此遗留的已知边界。

## 4. 崩溃一致性测试

### 4.1 崩溃注入手段

由于 Asterinas 不提供 device-mapper，xfstests 中依赖 `dm-log-writes`、`dm-flakey` 的崩溃注入用例无法直接运行。本系统以自研的崩溃注入场景补位（`test/initramfs/src/syscall/ext4_crash/`），其原理是在 JBD2 生命周期的关键语义点——提交记录写出之前、之后，以及检查点回写之前——注入模拟掉电，随后重新挂载并校验数据。这一手段在语义上与 `dm-log-writes` 的"在某 I/O 屏障处截断"等价，但更贴合本系统的内部时序，能够精确地把崩溃落在我们关心的次序边界上。

### 4.2 结果

| 测试 | 结果 |
|---|---|
| JBD2 崩溃恢复矩阵（Phase 1） | 9 / 9 PASS |
| JBD2 崩溃恢复矩阵（Phase 2/4，多场景） | 18 / 18 PASS |
| host-crash fsync 持久化 | 4 / 4 PASS |

### 4.3 恢复语义的范围声明

崩溃恢复的保证范围被主动声明，以避免过度宣称。对 guest 崩溃（虚拟机内崩溃、进程被杀、模拟掉电），重新挂载后重放已提交事务，CRC 校验显示数据一致性 100%；这建立在"提交记录落盘即事务完整"的屏障不变量之上（提交块前有设备 sync 屏障，fsync 尾部有最终 flush）。对 host 掉电，一致性依赖更强的假设——virtio 同步写完成即意味着有序持久化；该假设在答辩中须主动声明（与 Phase 3 文档一致）。此外，第 11 节指出崩溃矩阵尚未覆盖"元数据块释放后被数据复用且检查点前崩溃"这一特定时序，对应 JBD2 撤销记录尚未写盘的已知边界。

## 5. 并发正确性测试

并发正确性以两层互补证据支撑，二者从不同角度逼近"无数据错乱、丢失"这一目标，且均被纳入守底、不得回退。

**自研确定性校验**。`phase2_concurrency.c`（`test/initramfs/src/syscall/ext4_phase2/`）以多个 worker 对多个文件执行确定性的读写序列，并对每个文件的最终内容做哈希校验；由于写入序列由种子决定，期望内容可被独立计算，从而把"是否发生错乱"判定为可机械裁决的等值比较。基线配置 `WORKERS=4 ROUNDS=8 SEED=78` 下结果为 7 / 7 PASS。

**标准并发套件**。xfstests 的 `concurrency` 套件（`PHASE4_DOCKER_MODE=concurrency`）以 fsstress 施加多进程随机系统调用压力，叠加崩溃恢复与并发直接 I/O，结果为 10 / 10 PASS。它的价值在于以非确定性的、贴近真实应用的负载补充自研用例的确定性覆盖。

**并发可扩展性**。在功能正确之外，并发改造的性能效果以 fio 在同一文件上的多线程直接 I/O 衡量。共享锁直接 I/O 改造（《架构设计文档》第 6.4 节）之后，1 MiB 块的并发写测得：

| 目标 | 线程数 | Asterinas (MB/s) | Linux (MB/s) | 比值 |
|---|:--:|---:|---:|---:|
| ext4 写（带日志） | 2 | 6024 | 3641 | 165.5% |
| ext4 写（带日志） | 4 | 5139 | 2750 | 186.9% |

对这组数据须给出诚实的解读。并发写随线程数近似线性扩展、并对齐 Linux 的共享锁语义，这一可扩展性是真实且可复现的，说明此前"per-inode 互斥锁横跨设备等待导致单文件吞吐封顶"的瓶颈已被拆除。但 165% / 187% 的绝对比值含有宿主写回缓存的放大效应——fio 仅在关闭时执行 fsync，对 Asterinas 与 Linux 同等放大——因此该数值只能作为并发可扩展性的佐证，而不代表裸盘的持久化吞吐。系统持久化的真实能力由 fsync（延迟约 2.37 ms，与 Linux 同量级）与崩溃恢复（18/18）共同保证。

## 6. 持久化语义测试

持久化语义的验证目标是确认 `fsync`、`fdatasync` 与设备 flush 在本系统上构成与 Linux 等价的持久化屏障，而非仅仅返回成功。

| 验证 | 结论 |
|---|---|
| ext4 常规文件 `fsync` / `fdatasync` | 等价于 Linux 持久化屏障：提交块前发起 PREFLUSH，VFS 尾部发起 final flush |
| raw 块设备 `fsync` | 触发真实的设备 flush |
| `bs=16K + fsync=4` 的真实成本 | ext4 journaled 写 5.415 MB/s 对 Linux 22.649 MB/s（该 fsync-heavy 结果仅用于验证语义代价，不作吞吐宣称） |

这里有一条必须坚持的口径纪律：`bs=16K fsync=4` 在语义收口之前曾给出过高的"性能"读数，那是因为彼时 fsync 并未真正触达设备 flush；语义收口后，该路径的真实成本显著高于此前的假象。因此该组数据只用于证明持久化语义正确，绝不用于性能宣传。

## 8. 性能测试结果

性能结果在此仅作汇总陈列，其归因、优化技术与上限分析见《性能优化技术研究报告》。

### 8.1 fio O_DIRECT 顺序读写（诚实口径，相对 Linux EXT4）

| 块大小 | 读 | 写 |
|---|---:|---:|
| 4K | 86.4% | 75.5% |
| 16K | 84.4% | 75.8% |
| 64K | 86.9% | 84.1% |
| 256K | 94.8% | 121.1% |
| 1M | 122.9% | 88.3% |

优化前小块读仅 16–24%、写 4K 仅 20%、写 1M 仅 63%。大块（256K、1M）已追平乃至反超 Linux；小块的剩余缺口与 Asterinas 原生 ext2 在同平台的 82–85% 上限一致，据此归因于 virtio 设备往返这一平台层、跨文件系统通用的开销，而非本 ext4 实现的短板（论证见研究报告第 6 节）。

### 8.2 SQLite speedtest1 真实应用（`--size 1000`，`page_cache=1`）

| 文件系统 | 总耗时 | 相对 Linux |
|---|---:|---:|
| ext4（带日志，本实现） | 234.9s | **21.92%** |
| ext2（无日志，Asterinas 原生） | — | 94.91% |
| ramfs（内存盘） | — | 95.87% |
| Linux ext4（对照） | ~52s | 100% |

相对 Linux 的占比从起点 2.97% 提升至 21.92%（7.4 倍），墙钟耗时由 2022s 降至 234.9s，全程 `PRAGMA integrity_check` 通过。三文件系统对照（ext2 94.91% / ramfs 95.87%）表明剩余差距来自带日志写路径的结构性成本，而非平台本身（详见研究报告第 3、7 节）。

## 11. 未覆盖范围与已知边界

诚实地界定测试的边界与界定其覆盖同等重要。下列各项为当前尚未闭合的部分：

| 项 | 状态 |
|---|---|
| official xfstests 全量 | 收口中：full run 在个别用例中断（堆分配错误，或 mmap 开页缓存触发更底层崩溃），已隔离 |
| JBD2 撤销记录写盘 | 未实现：崩溃矩阵尚未构造"元数据块释放后被数据复用且检查点前崩溃"的精确时序，对应数据覆盖风险（guest-crash 全覆盖场景不触发），验证设计见附录 A-1 |
| hardlink / symlink | 未实现 |
| ENOSPC 半成品元数据 | 待补 shutdown 只读保护，并以 e2fsck 验证一致性 |

需要再次强调：守底套件全绿不等于不存在覆盖洞。撤销记录缺口是一个已知的、已被定位的崩溃一致性边界，已在《架构设计文档》第 5.4 节与《差异化分析》中声明，并列入后续 hardening；它之所以未在现有矩阵中暴露，是因为现有用例没有构造触发它所需的块复用时序，而非因为它不存在。

## 附录 A：关键验证实验设计（待补与加固）

下列实验用于覆盖第 11 节指出的边界，是后续 hardening 的验证设计。

| 实验 | 步骤 | 判定 |
|---|---|---|
| A-1 块复用崩溃（验证撤销缺口） | 建大目录撑出目录/树块 → 删整目录 → 建大文件复用同批块 → fsync → 在检查点前杀虚拟机 → 重新挂载比对文件 CRC | CRC 不变为 PASS；若出现 extent 魔数或目录项样式的外来内容，即复现该缺口 |
| A-2 ENOSPC 半成品（验证失败回滚） | 填盘至接近满 → 并发追加直至 ENOSPC → 正常 umount → e2fsck | fsck 零错误为 PASS |
| A-3 mmap 脏页 | mmap 写但不 msync → fsync → 杀虚拟机 → 重新挂载比对 | 数据在为 PASS |
